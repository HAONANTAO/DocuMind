---

## Why this project

Large language models can't read your private documents — they only know what's in their training data. DocuMind closes that gap with a full RAG pipeline: it indexes any PDF into a vector database, retrieves the most relevant passages at query time, and feeds them into GPT-4o-mini with strict grounding instructions. The result is a document Q&A experience that is fast, accurate, and traceable to the source.

It is built end-to-end as a multi-tenant SaaS — auth, plan limits, async indexing, streaming, security hardening, and per-user data isolation — not just a notebook demo.

---

## Engineering highlights

- **End-to-end RAG pipeline** — PDF parsing → recursive chunking (1,000 chars / 200 overlap) → OpenAI embeddings → Pinecone vector store → similarity retrieval → grounded prompt assembly → streamed generation.
- **Server-Sent Events streaming** — Tokens are flushed to the browser as they're generated by the LLM, giving a sub-second time-to-first-token feel; sources are emitted as a final JSON event after the stream closes.
- **Async upload + status polling** — `POST /documents/upload` returns immediately with a `processing` status; embedding/indexing runs in the background, and the frontend reflects `uploading → processing → ready/error` in real time.
- **Per-tenant vector isolation** — Each user gets a dedicated Pinecone namespace (`user_<userId>`), and every MongoDB query is scoped by `userId`. Vectors and documents physically cannot leak across accounts.
- **Production security baseline** — Helmet headers, strict CORS that *refuses to start* without `ALLOWED_ORIGIN` in production, `express-rate-limit` on auth and chat routes, `zod` schema validation at every input boundary, bcrypt password hashing, and generic auth errors to prevent user enumeration.
- **Multi-turn conversational memory** — The last 6 turns are injected into the prompt so follow-up questions like *"and what about the second one?"* resolve correctly.
- **Free-plan quotas** — Per-user, weekly-rolling counters for documents and questions, surfaced in the UI as live usage bars.

## Architecture

### Indexing — runs once, on PDF upload

```
PDF ──▶ pdf-parse ──▶ RecursiveCharacterTextSplitter ──▶ OpenAI Embeddings ──▶ Pinecone
                       (1,000 chars, 200 overlap)        (text-embedding-3-small)   (namespace: user_<id>,
                                                                                     metadata: documentId,
                                                                                     chunkIndex)
```

### Query — runs on every chat message

```
Question ──▶ Embed question ──▶ Pinecone top-k=5
                                (filter: documentId,
                                 namespace: user_<id>)
                                       │
                                       ▼
              ┌──────────────────────────────────────────────────┐
              │ Prompt: system + retrieved chunks + last 6 turns │
              └──────────────────────┬───────────────────────────┘
                                     ▼
                        gpt-4o-mini (LangChain stream)
                                     │
                       ┌─────────────┴─────────────┐
                       ▼                           ▼
              SSE → frontend            MongoDB (Conversation:
              (tokens + sources)         messages + sources)
```

## Key design decisions

**Why chunk size 1,000 / overlap 200?**
A 1,000-character chunk is large enough to carry a self-contained idea (a paragraph or two) but small enough that 5 chunks comfortably fit in `gpt-4o-mini`'s context with room for history. The 20% overlap stops a sentence from being split awkwardly across two chunks, which would otherwise cause both halves to score poorly in similarity search.

**Why per-user Pinecone namespaces?**
Multi-tenancy via metadata filters works, but namespaces give a stronger isolation guarantee — a buggy filter clause cannot accidentally retrieve another user's vectors. It also keeps deletes cheap: removing a user wipes their namespace in one call.

**Why SSE instead of WebSockets?**
Chat is one-way streaming (server → client). SSE is a single HTTP request with auto-reconnect built in, plays nicely with Express middleware, and avoids the operational complexity of a WebSocket gateway. A WebSocket would only pay off if we needed full duplex (e.g. typing indicators).

**Why async indexing instead of blocking the upload response?**
Embedding a 50-page PDF takes 5–15 seconds. Holding the HTTP connection open for that long is a poor UX (no progress feedback) and brittle (any proxy timeout breaks the upload). Returning immediately with `status: "processing"` lets the UI show a progress card while a background task does the work.

**Why `gpt-4o-mini` over `gpt-4o`?**
Roughly 30× cheaper, fast enough for streaming feel, and accuracy is bottlenecked by retrieval quality rather than model capability for grounded extractive Q&A. Switching tiers is a one-line config change if a workspace ever wants premium quality.

## API reference

Base URL: `https://<your-backend>/api`. All protected routes require `Authorization: Bearer <jwt>`.

### Auth

| Method | Path | Auth | Description |
|---|---|---|---|
| POST | `/auth/register` | — | Create account |
| POST | `/auth/login` | — | Login, returns JWT |
| GET | `/auth/me` | ✓ | Current user profile |
| GET | `/auth/usage` | ✓ | Plan usage stats |

```jsonc
// POST /auth/login
{ "email": "user@example.com", "password": "yourpassword" }

// → 200 OK
{ "token": "<jwt>", "user": { "_id": "...", "email": "...", "plan": "free" } }
```

### Documents

| Method | Path | Auth | Description |
|---|---|---|---|
| POST | `/documents/upload` | ✓ | Upload PDF (`multipart/form-data`, field `file`, ≤20 MB) |
| GET | `/documents` | ✓ | List user's documents |
| DELETE | `/documents/:id` | ✓ | Delete document + vectors |

Status lifecycle: `uploading → processing → ready | error`.

### Chat

| Method | Path | Auth | Description |
|---|---|---|---|
| POST | `/chat` | ✓ | Ask a question, streams response (SSE) |
| GET | `/chat/:documentId/history` | ✓ | Conversation history |

```jsonc
// POST /chat
{ "documentId": "<id>", "question": "What are the key findings?" }

// → text/event-stream
// raw tokens streamed as generated, then a final JSON event:
{
  "done": true,
  "sources": [
    { "content": "...chunk text...", "metadata": { "documentId": "...", "chunkIndex": 3 } }
  ]
}
```

## Security

- **Helmet** for CSP, X-Frame-Options, X-Content-Type-Options, etc.
- **Strict CORS** — production server refuses to boot without `ALLOWED_ORIGIN`; no `*` fallback.
- **Rate limiting** — `/auth/*`: 10 attempts / IP / 15 min; `/chat/*`: 30 req / user / minute (keyed by JWT user id).
- **Input validation** — every user-provided body is validated with `zod` before reaching business logic.
- **Password rules** — ≥8 chars with at least one letter and one digit; bcrypt cost 10.
- **No user enumeration** — `/auth/login` returns the same generic error for unknown email vs. wrong password.
- **Per-tenant data isolation** — every MongoDB query is scoped by `userId`; Pinecone uses one namespace per user.

### Known limitations

- **JWT in `localStorage`** — vulnerable to XSS if a dependency is compromised. Mitigated today by strict CSP and no raw `dangerouslySetInnerHTML` (markdown is DOMPurify-sanitised). Migrating to httpOnly cookie + CSRF token is on the short-term roadmap.
- **No automated test suite yet** — the controls above are reviewed manually. An integration suite (auth, rate-limit, CORS, RAG end-to-end) is the next priority.

## Local development

<details>
<summary>Click to expand setup instructions</summary>

### Prerequisites
- Node.js 18+
- MongoDB (Atlas or local)
- Pinecone account with an index named `documind` (1,536 dims, cosine)
- OpenAI API key

### Backend

```bash
cd backend
npm install
```

Create `backend/.env`:

```env
PORT=3001
MONGODB_URI=your_mongodb_connection_string
JWT_SECRET=your_jwt_secret_at_least_32_chars
PINECONE_API_KEY=your_pinecone_api_key
PINECONE_INDEX=documind
OPENAI_API_KEY=your_openai_api_key
ALLOWED_ORIGIN=http://localhost:3000
```

```bash
npm run dev      # nodemon, hot reload
npm start        # production
```

Backend listens on `http://localhost:3001`.

### Frontend

```bash
cd frontend
npm install
cp .env.example .env.local   # then fill REACT_APP_API_URL=http://localhost:3001/api
npm start
```

Frontend at `http://localhost:3000`.
